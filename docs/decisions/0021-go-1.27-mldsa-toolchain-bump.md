# ADR 0021: Bump the `go` directive to 1.27.0 for `crypto/mldsa`

## Status

Accepted.

## Context

Step 4 Part B requires ML-DSA-87 (FIPS 204) support in `internal/trust`'s crypto-agile
root/verification formats. Go's standard library gained `crypto/mldsa` in Go 1.27 (Go 1.27
release notes, "New crypto/mldsa package": "The new `crypto/mldsa` package implements the
post-quantum ML-DSA signature scheme specified in FIPS 204."). `crypto/x509` in the same
release gained matching `ParsePKIXPublicKey`/`MarshalPKIXPublicKey` support for
`*mldsa.PublicKey` (confirmed locally: `go1.27.4`'s `crypto/x509/x509.go:31,120-156` and
`crypto/x509/parser.go:374`).

This repository's `go.mod` declared `go 1.26.0` with `toolchain go1.27.4`: the toolchain
already in use was new enough, but the `go` directive (the module's own minimum language
version) was not, which is misleading for any future reader or tool that checks it to
decide whether `crypto/mldsa` is safe to import.

## Decision

Bump the `go` directive from `1.26.0` to `1.27.0`, in its own commit, before any code
change that imports `crypto/mldsa`. `toolchain go1.27.4` is unchanged (already satisfies
the new minimum).

### FIPS-module implications

`crypto/mldsa`'s own doc comment: "This package is unavailable if using the FIPS 140-3 Go
Cryptographic Module v1.0.0, in which case `GenerateKey`, `NewPrivateKey`, `NewPublicKey`,
and `Verify` will return an error." Confirmed by reading
`crypto/mldsa/mldsa_fips140v1.0.go` (`//go:build fips140v1.0`) directly: every one of those
four functions is stubbed to return a fixed `errUnavailable` (`NewPublicKey`, `Verify`) or
panic (methods that cannot be reached because no `*PublicKey`/`*PrivateKey` can ever be
constructed). `crypto/x509.ParsePKIXPublicKey` for an ML-DSA SPKI also fails under this
build tag, since it calls `mldsa.NewPublicKey` internally (`crypto/x509/parser.go:374`).

This means: if `tetragon-relay` is ever built with `GOFIPS140=v1.0.0` (or any future
module version that still excludes ML-DSA), every operation on an `mldsa-87` key —
including just parsing its SPKI DER via the standard library — becomes unavailable.
`internal/trust`'s root-metadata parser (B1/B2) is written so that an `mldsa-87` key entry
is still accepted *structurally* (its keytype/OID match is checked independently of
`crypto/x509`/`crypto/mldsa`, via a direct `encoding/asn1` read of the SPKI's
`AlgorithmIdentifier`, before any attempt to construct a usable `*mldsa.PublicKey`); only
the point where a signature actually needs ML-DSA verification lazily calls
`mldsa.NewPublicKey`/`mldsa.Verify`, and only that call — not root-metadata parsing as a
whole — fails closed when the build lacks ML-DSA. See
`docs/decisions/0022-crypto-agility.md` for the full design.

No production deployment of this project currently sets `GOFIPS140=v1.0.0`; this ADR
records the interaction for the day one does (architecture doc section 9, FIPS crypto
policy on RHEL 9).

## Consequences

- `go.mod`'s `go` line is `1.27.0`; `toolchain` stays `go1.27.4`.
- No vendored dependency needed: `crypto/mldsa` is standard library.
- `make ci`'s reproducible-build check, vendor-check, and every Linux-only path are
  re-verified green on GitHub Actions after this bump (recorded in
  `docs/reports/step-04a.md`).
- If this project is ever built under `GOFIPS140=v1.0.0`, any root metadata that *requires*
  (not merely contains) an `mldsa-87` key in a role's `require_keytypes` becomes
  permanently unusable for that role until a non-FIPS-v1.0.0 toolchain is used — which is
  the correct fail-closed behavior (B5 keeps every production role `ecdsa-p384`-only today,
  so this does not affect current deployments).
